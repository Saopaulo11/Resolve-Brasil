# Resolve Brasil

AI case manager для бразильских потребителей. Пользователь рассказывает, что
случилось, обычными словами; сервис помогает понять ситуацию, собрать
документы, свериться с официальными источниками и дойти до следующего шага.

**Conte o que aconteceu. Descubra o que fazer.**

Действия — отправку сообщений, жалоб и документов — всегда совершает сам
пользователь. Resolve Brasil не адвокат, не государственный орган и не
представитель пользователя.

## Статус: PHASE 12 (оценка качества AI)

Готовы основание, вход, дела, анализ, документы, источники, разбор ответа
компании, напоминания, обезличенная аналитика, админка и центр приватности: Express + TypeScript, схема
PostgreSQL на Prisma, вход по телефону и одноразовому коду, сессии,
раздельные согласия, дела с хронологией, интеграция с OpenAI Responses API
со структурированным выводом и валидацией, классификатор, вопросы, план
действий, черновик письма компании, загрузка документов в приватное
хранилище, подтверждение извлечённых данных пользователем, база
официальных источников с обязательной проверкой адресов, разбор ответа
компании — текстом или файлом, напоминания с доставкой через абстракцию
каналов, конвейер Consumer Intelligence с защитой малых групп и
администрирование с RBAC и журналом обращений, выгрузка своих данных,
удаление по запросу и применение сроков хранения. Админка доведена до
полного состава §50 — одиннадцать разделов, каждый за своим правом, — а
ответы AI теперь можно оценить, и оценки видны в ней же.

Без ключа провайдера интерфейс **не показывает выдуманного разбора** и прямо
говорит, что анализ не выполнялся: правдоподобная заглушка неотличима от
настоящего ответа модели, и это хуже пустоты.

## Быстрый старт

```bash
npm install
cp .env.example .env     # минимум: DATABASE_URL и SESSION_SECRET
npm run db:generate
npm run dev              # http://localhost:3000
```

Без `DATABASE_URL` сайт поднимется целиком, включая вход: данные лягут в
хранилища в памяти процесса и исчезнут при перезапуске. `/health` при этом
честно ответит `503`. Так сделано намеренно — разрабатывать и проверять вход
можно до появления базы, а в production эта развилка недостижима:
`loadConfig()` там требует `DATABASE_URL`.

Код OTP без настоящего провайдера печатается в лог (`MOCK OTP para ...`) —
это единственный способ войти локально. В production такой провайдер
отказывается запускаться.

### База данных

```bash
npm run db:deploy    # накатить миграции (production и CI)
npm run db:migrate   # создать новую миграцию при правке схемы
```

Первая миграция лежит в `prisma/migrations/20260923000000_init` — 24 таблицы,
47 индексов, 24 внешних ключа. Она накатана на настоящий PostgreSQL 16 и
проверена на расхождение со схемой: `prisma migrate diff` возвращает пустой
результат. Тот же диф стоит шагом в CI — правка `schema.prisma` без
миграции не пройдёт, потому что в production она не применится.

### Проверки

```bash
npm run lint
npm run typecheck
npm test
npm run build
```

Набор `tests/integration/prismaStores.test.ts` гоняет реализации на Prisma
против настоящего PostgreSQL и пропускается без `DATABASE_URL`. Остальные
тесты работают на хранилищах в памяти: поднимать базу ради `npm test` никто
не станет, а тест, который нужно включать руками, просто закомментируют. В
CI база поднимается сервисом, поэтому там выполняется всё.

### Приватность

```bash
npm run privacy:retention   # применить сроки хранения
npm run privacy:deletions   # исполнить наступившие запросы на удаление
```

Запускать по расписанию. Обе команды удаляют данные безвозвратно — сначала
файлы из хранилища, потом записи: обратный порядок оставил бы файлы без
ссылок, то есть навсегда.

### Администрирование

```bash
npm run admin:create -- admin@exemplo.com OWNER
```

Пароль не принимается аргументом: аргументы видны в истории оболочки и в
списке процессов. Команда генерирует стойкий пароль, печатает его один раз
и хранит только хеш.

Роли: `VIEWER` (сводка), `SUPPORT` (дела), `ANALYST` (аналитика), `ADMIN`
(всё перечисленное плюс журнал и источники), `OWNER` (плюс управление
администраторами).

Разделы `/admin`:

| Раздел | Право | Что показывает |
| --- | --- | --- |
| Painel | `dashboard.view` | сводка по делам |
| Casos | `cases.list` | номер, категория, компания, статус, дата |
| Analytics | `analytics.view` | агрегаты, включая разрез по ситуации Pix |
| Usuários | `users.list` | телефон последними цифрами, число дел, дата |
| Empresas | `companies.view` | справочник компаний, отрасль и слово-основание |
| Documentos | `documents.list` | тип, размер, состояние — без имени файла |
| IA | `ai.view` | вызовы модели: токены, время, оценка стоимости |
| Fontes | `sources.manage` | источники и состояние их проверки |
| Avaliações | `feedback.view` | оценки ответов AI и причины |
| Notificações | `notifications.view` | доставка: канал, шаблон, ошибка |
| Acessos | `audit.view` | журнал обращений администраторов |
| Configurações | `settings.view` | действующая конфигурация без значений ключей |

Право `documents.read` есть в матрице, но не выдано ни одной роли —
см. ниже.

### Аналитика

```bash
npm run analytics:report              # внутренний отчёт
npm run analytics:report loja-exemplo # срез по компании
```

Команда, а не страница: веб-дашборд без авторизации админа означал бы
открытый доступ к агрегатам, а авторизация — это PHASE 10.

### Оценка качества модели

```bash
npm run ai:eval            # прогон набора: категория и запреты
npm run ai:eval -- --deep  # плюс план действий и черновик письма
```

Набор лежит в `evals/dataset.json` и **весь выдуман** (§82). Это не
оговорка в комментарии, а условие загрузки: каждое дело обязано нести флаг
`synthetic`, а название компании — слово «Exemplo». Выдуманная жалоба на
настоящую компанию — это не тестовые данные, а клевета.

Прогон меряет три вещи: попадание в категорию, уверенную ошибку (модель
уверена и неправа — такую никто не перепроверит) и нарушения запретов §3,
§9 и §30. Нарушение — не процент, а брак: одного достаточно, чтобы прогон
считался проваленным при любой точности.

С `AI_PROVIDER=mock` команда отказывается работать: заглушка возвращает
пустой результат, и цифры прогона были бы цифрами о заглушке (§79).

### Напоминания

```bash
npm run reminders:dispatch   # отправить наступившие напоминания
```

Запускать по расписанию — например раз в час. Команда берёт наступившие
напоминания, отправляет их через настроенный канал и отмечает результат.
Неудачная доставка повторяется ограниченное число раз, потом напоминание
отменяется, а причина остаётся в журнале уведомлений.

### Официальные источники

```bash
npm run sources:import   # завести кандидатов из sources/candidates.json
npm run sources:verify   # открыть каждый адрес и проставить дату проверки
```

Импорт ничего не подтверждает — он только заводит записи. Подтверждением
считается лишь успешная проверка, и запускать её нужно там, где есть доступ
в сеть. Пока источников нет, план действий честно пишет, что процедуру
подтвердить не удалось: это ожидаемое поведение, а не сбой.

Те же четыре команды гоняет CI — без базы и без ключей провайдеров.

### Решения, на которых всё держится

**PostgreSQL — source of truth.** Состояние дела живёт у нас, а не в
AI-провайдере. Модель получает выборку фактов и возвращает структуру; после
валидации она ложится в базу.

**Три типа информации не смешиваются.** Факт от пользователя, официальный
источник и предположение AI — разные вещи. В базе это `FactSource`, в
интерфейсе — разная подача. Смешать их значит выдать догадку за право.

**Вывод модели не показывается напрямую.** Сначала схема (`src/ai/schemas.ts`),
потом бизнес-правила. Неизвестное поле или неверный тип — ошибка обработки,
а не повод показать «как есть».

**Пределы полей не уходят модели, а проверяются у нас.** В схему для
structured outputs попадает только форма ответа: набор ключевых слов,
который принимает строгий режим, со временем менялся, и неподдержанное
слово означало бы ошибку 400 на каждом запросе. Длины и диапазоны
проверяет наша валидация уже после ответа — там, где это и должно
проверяться.

**Модель не ищет источники, а выбирает из данных ей.** Список официальных
источников приходит из нашей базы, и ответ дополнительно фильтруется по
нему. Выдуманная ссылка на gov.br — самая убедительная и самая опасная
ошибка, какую может сделать модель, и запрет на неё сделан структурным,
а не словесным.

**Удаление не мгновенное — и это защита, а не удержание.** Захваченная
учётная запись иначе позволяет стереть все дела одним нажатием, и владелец
узнаёт слишком поздно. За время отсрочки он успевает отменить. Подтверждение
словом, а не галочкой: удаление необратимо.

**Срок хранения дела считается от закрытия, а не от создания.** Дело в
разгаре не исчезает по таймеру — оно живёт, сколько нужно человеку.

**В выгрузке телефон и рассказ показаны целиком.** Это данные самого
человека, и право на них у него есть; маскирование, уместное в журналах и
в админке, здесь было бы издевательством.

**Обезличенные слепки при удалении остаются.** В них нет ничего, что ведёт
к человеку, и связи с делом у них тоже нет — удалять нечего.

**Документы не доступны ни одной роли администратора.** Ни поддержке, ни
владельцу. Это паспорта, выписки и переписка живых людей; для работы они не
нужны, а один доступ «на всякий случай» становится постоянным. Когда такая
нужда появится, это будет отдельная роль с отдельным обоснованием, а не
тихо добавленная строка в существующую.

**Экран настроек не показывает значений ключей.** Ни одной роли и никогда —
только «configurado» или «não configurado». Настройки, показывающие ключ,
превращают любой вход в админку в утечку ключа, а вход в админку защищён
паролем, а не тем, чем защищён сам ключ.

**Имя файла в админке не показывается.** «cpf-joao.pdf» говорит достаточно
и без содержимого: имя обычно называет и документ, и человека. В разделе
документов остаются тип, размер, формат и состояние — всего этого хватает,
чтобы понять, работает ли загрузка.

**«Não verificado» не означает «чисто».** Пока антивирус не подключён,
состояние проверки показывается как отсутствующее. Подставить туда
«чисто» значило бы сообщить сотруднику то, чего никто не проверял.

**Оценка привязана к сообщению, а не к делу.** «Не помогло» без указания,
что именно не помогло, ни о чём не говорит. Повторное нажатие не создаёт
второй записи: иначе одно мнение засчитывалось бы столько раз, сколько
человек нажал кнопку. У положительной оценки причина не сохраняется — иначе
«ajudou» с причиной «informação incorreta» попал бы в отчёт как жалоба.

**Доля «помогло» не показывается на крошечной выборке** — по тому же
правилу, что и остальные проценты (§57). «100 % полезно» при одной оценке —
цифра, которой нельзя пользоваться.

**Учёт вызовов модели хранит только метрики.** Провайдер, модель, операция,
токены, время, успех. Ни текста запроса, ни ответа, ни ключей: таблица
учёта с содержимым — это вторая копия переписки, которую никто не собирался
хранить. Стоимость считается по ценам из конфигурации; цены не заданы —
стоимость не показывается, потому что выдуманная цифра выглядит
достоверной.

**Оценка модели проверяет не «хороший ответ», а брак.** Вкус измерять
нечем, а вот обещание результата, роль адвоката, номер закона без
официального источника, ссылка на неофициальный сайт и протокол, которого
человек не называл, — проверяются механически. Слова «garantia» в списке
запретов намеренно нет: гарантия на товар — законное понятие
потребительского права, и запрет на него ломал бы правильные ответы, а
сломанную проверку через неделю отключают.

**Границы слов в проверках заданы через Unicode, а не `\b`.** В JavaScript
`\b` считает буквами только ASCII, поэтому «você» и «receberá» ломают
выражение молча: оно перестаёт срабатывать, но выглядит рабочим.

**Точность считается только от дел, дошедших до ответа.** Иначе сбой сети
выглядел бы как ошибка модели. Дела без ответа при этом не прячутся — они
считаются отдельно и сами по себе проваливают прогон.

**Реализации на Prisma проверяются на настоящей базе.** Тесты на хранилищах
в памяти быстрые, но при них код Prisma не выполняется ни разу, и
расхождение со схемой обнаружилось бы в production. Отдельный набор гоняет
каждое хранилище против PostgreSQL: включая то, что `Decimal` возвращается
числом, `Json` — объектом, каскады уносят документы вместе с делом, а
обезличенный слепок переживает удаление пользователя.

**Подтверждённый факт становится полем дела, догадка — нет.** До
подтверждения извлечённое значение живёт только в списке фактов. После —
переносится в дело: компания, сумма, способ оплаты, даты. Пересобирается
весь набор, а не одно поле: человек мог отклонить подтверждённое раньше, и
тогда поле обязано опустеть, а не остаться от прошлого решения.

**Разбор значения умеет отказываться.** «uns duzentos reais» и «semana
passada» в поля дела не попадают — факт остаётся в списке, человек его
видит, а наполовину разобранная сумма уходит в аналитику как настоящая, и
проверить её потом нечем.

**Компании сопоставляются по написанию, а не по похожести.** «Loja Exemplo
S.A.» и «LOJA EXEMPLO LTDA» — одна компания; «Loja Exemplo» и «Loja Exemplo
Digital» — разные. Умное сопоставление вроде «magalu ≈ Magazine Luiza»
требует справочника настоящих компаний, которого у нас нет и выдумывать
нельзя. Такие соответствия заводит человек, и до его отметки алиас ничего
не объединяет: склеенные по ошибке компании потом не разделить.

**Отрасль берётся из того, что компания сказала о себе сама.** «Banco …»,
«… Seguros», «… Telecom» — это признак в названии, а не знание о рынке.
Рядом с отраслью в админке показано слово, давшее ответ: без него ошибка
правила невидима, потому что отрасль выглядит одинаково достоверно и когда
угадана, и когда выведена. Ни одно правило не сработало — «не
определено», и в отчёте это читается не как «прочее».

**Дело закрывает человек, а не мы.** У нас нет способа узнать, вернулись
ли деньги, поэтому «resolvido» — это его слова, USER_FACT в хронологии, а
не наш вывод. Исходов два, и оба честные: «решено» и «закрыто без
решения». Свести их к одному «завершено» значило бы считать каждое
брошенное дело успехом.

**Дата закрытия ставится вместе со статусом.** Без неё срок хранения (§65)
не наступает никогда — закрытое дело остаётся в базе навсегда, — а медиана
времени до решения не считается вовсе. Возврат дела в работу дату снимает,
иначе срок хранения удалил бы дело, которое ведут прямо сейчас.

**Жалобу в Procon подаёт человек.** Переход на другой канал — это запись
того, что он сделал сам: мы не подаём за него и не представляем его ни
перед кем (§3). Порядок каналов подсказывает следующий шаг, но не
запрещает остальные: пойти сразу в Procon — его право.

**Выход со всех устройств есть, потому что пароля нет.** Вход по номеру и
коду менять нечего: если телефон у чужого человека, отзыв всех сессий —
единственное, что обрывает доступ. Текущая сессия отзывается вместе с
остальными: «все» значит все, иначе человек решит, что вышел, а на этом
устройстве останется вошедшим.

**Ситуацию с Pix выбирает человек.** Pix — основной способ оплаты в
Бразилии, и разные беды с ним ведут в совершенно разные стороны:
мошенничество, перевод не тому, спор с реальной компанией. Отличить их по
рассказу нельзя, а ошибка здесь уводит дело не туда — поэтому система не
догадывается, а спрашивает, и ответ становится USER_FACT. Вопрос
показывается только там, где платили через Pix: в остальных делах это поле
было бы непроверяемым мусором в аналитике.

**Сроков и процедур Pix в коде нет.** Ни числа дней, ни названия
механизма: они меняются и обязаны приходить из проверенного официального
источника (§9, §30, §32), а не из строки, которую никто не перечитывает.
В аналитику идёт категория ситуации, а не идентификатор перевода — сам Pix
не попадает туда никогда (§56).

**Видно, на что опиралось дело.** Источники, использованные в плане,
запоминаются за делом и попадают в выгрузку данных: план показывает ссылки
сейчас, а через месяц без этой связи непонятно, что именно ими
подтверждалось. Связываются только источники из нашей базы — адрес,
который модель вернула сама, туда не попал и попасть не должен (§30).

**Штат спрашивается, город — нет.** Procon у каждого штата свой, и без
штата на вопрос «куда идти» ответить нечем — поэтому он в форме и уходит
модели. Город не спрашивается вовсе: вместе с суммой, категорией и месяцем
он опознаёт человека не хуже имени, а для выбора канала не нужен. Штат
необязателен: «предпочитаю не указывать» — законный ответ, а не ошибка
формы.

**Список штатов закрытый.** Введённый руками код даёт штат, которого нет, и
дело уходит в несуществующий канал.

**Права — матрица, а не условия по коду.** Разбросанные проверки «если роль
ADMIN» невозможно охватить взглядом, и однажды одна из них окажется
забытой. Матрица видна целиком, и тест сверяет её с ожиданием, включая то,
что права расширяются вдоль лестницы ролей без дыр в середине.

**Вход админа отделён от пользовательского во всём:** своя кука с
`Path=/admin` и `SameSite=Strict`, своя таблица сессий, срок жизни в часах
вместо месяца. Общая инфраструктура рано или поздно приводит к
пользовательской сессии с правами администратора.

**Пароли на scrypt из стандартной библиотеки.** Обычный хеш подбирается со
скоростью миллиардов вариантов в секунду. Параметры хранятся рядом с хешем,
чтобы поднять их через год, не ломая существующие пароли. Проверка идёт
даже при несуществующем администраторе — иначе время ответа само отвечает,
заведена ли учётная запись.

**Из аналитики нет пути к человеку.** В слепке дела нет телефона, email,
CPF, имени, адреса, текста обращения, документов и идентификатора
транзакции. Точная сумма заменена диапазоном, точная дата — месяцем: вместе
с городом и категорией они опознают человека не хуже имени. Ссылки на
`cases` и `users` нет — только псевдоним дела, односторонний хеш с
серверной солью. Без пригодной соли слепок не пишется вовсе.

**Группа меньше порога не показывается целиком.** Ни значение, ни название:
сегмент «дела по компании X в городе Y за март на 300–500» опознаёт
человека не хуже имени. Скрытое при этом не молчит — рядом всегда стоит,
сколько групп и сколько дел скрыто, иначе читатель сложит доли до ста
процентов там, где это неверно.

**Доля на крошечной выборке не считается.** Процент эскалаций по трём делам
вводит в заблуждение сильнее, чем прочерк. Срез по компании (§59) всегда
несёт период и размер выборки, а при малой выборке не показывается вовсе.
Рейтингов «худшие компании» нет и не будет: у нас не выборка по стране, а
дела, которые к нам пришли.

**Напоминание — услуга, а не рассылка.** Человек попросил напомнить о
своём деле; отказ от новостей этого не отменяет (§17). В журнале уведомлений
такое сообщение помечено как `SERVICO`, и ни телефон, ни текст туда не
пишутся — текст содержит подробности дела.

**Планировщика внутри процесса нет.** Рассылку запускает внешний cron
командой `npm run reminders:dispatch`. Свой таймер в процессе на нескольких
инстансах отправил бы одно и то же напоминание несколько раз одному
человеку.

**Ответ компании принимается как придётся.** Текстом или файлом —
скриншотом переписки, PDF письма, фотографией. Требовать перепечатать текст
со скриншота значит потерять человека ровно там, где он уже дошёл до
половины пути. Файл при этом проходит ту же проверку, что и любой документ
дела: отдельной облегчённой дороги для него нет.

**Сбой разбора не теряет ответ.** Ответ сохраняется и статус дела меняется
до вызова модели. Если разбор не удался, человек видит это и может
повторить — но принесённое им уже в деле.

**Непроверенный источник не существует.** Источник заводится выключенным и
без даты проверки. Пока `npm run sources:verify` не откроет адрес, он не
показывается пользователю и не уходит модели. Устаревшая проверка снимает
источник с использования так же, как отсутствие проверки: процедуры и
адреса меняются, и ссылка, поданная как подтверждённая, — это ровно то,
чего §30 не допускает.

**Официальным может быть только государственный домен.** `.gov.br`,
`.jus.br`, `.leg.br`, только по HTTPS. Это проверка на входе в базу, а не
пожелание в промпте: модель физически не может подсунуть блог, потому что
такого адреса в базе нет. Похожие домены вроде `gov.br.exemplo.com`
отвергаются.

**Тип файла решается по содержимому, а не по заявленному.** MIME и
расширение приходят от клиента и подделываются переименованием файла.
Решающей считается сигнатура в первых байтах: это отсекает самый дешёвый
обход — исполняемый файл с именем `comprovante.pdf`.

**Документ уходит провайдеру только по явному действию.** Это единственная
операция, где наружу идёт исходный файл, а не выборка полей. Она
запускается кнопкой на конкретном документе, а не автоматически при
загрузке.

**Извлечённое не становится фактом само по себе.** Данные из документа
создаются со статусом «ожидает подтверждения», и модели обратно уходят
только подтверждённые человеком. Иначе её собственная догадка вернулась бы
к ней как установленный факт и закрепилась.

**Неуверенная классификация не становится категорией дела.** Ниже порога
`AI_CLASSIFICATION_MIN_CONFIDENCE` разбор показывается как предположение, но
дело не переклассифицируется: неверная категория с виду уверенного ответа
уводит дело не туда, и заметить это потом некому.

**Аналитика отделена от персональных данных.** В `AnalyticsCase` и
`AnalyticsEvent` нет телефона, email, CPF, имени, адреса, сырой переписки и
документов: только месяц, диапазон суммы, категория и псевдоним. Связи с
`users` нет намеренно.

**Вход не отвечает, знаком ли номер.** Регистрация и вход — один путь с
одинаковыми ответами. Раздельные формы превратили бы страницу входа в
проверку базы телефонов.

**Рассказ не теряется на входе.** Человек описывает проблему до входа, и
описание длиной до 5000 символов в куку не помещается — она вмещает 4 КБ.
Поэтому дело создаётся сразу, без владельца, а привязывается после
подтверждения телефона. Перехватить чужое дело номером в куке нельзя:
привязка работает только для дела без владельца.

**Чужое дело неотличимо от несуществующего.** И то и другое даёт 404. Ответ
403 подтвердил бы, что такой номер существует, и публичные номера дел стали
бы способом проверять их наличие перебором.

**Запоздавшая SMS не наказывает пользователя.** Если человек успел запросить
новый код, а потом пришёл первый, старый код узнаётся как погашенный: вход
не даётся, но попытка не списывается. В Бразилии задержка SMS — обычное
дело, и без этого человек получал бы «неверный код» за чужую ошибку.

**Конфигурация читается лениво.** `loadConfig()` зовётся при старте сервера,
а не при импорте модуля: иначе `npm run build` и тесты начнут требовать
секреты, и CI без них не соберётся. В production нехватка обязательного —
это падение при старте, а не работа с небезопасным умолчанием.

## Безопасность

Строгая CSP без `unsafe-inline`, HSTS в production,
CSRF по схеме double-submit, сессии с токеном в куке и хешем в базе,
ограничение частоты (общее, для OTP по номеру, для AI по пользователю),
усечённые IP в журналах, редакция телефонов и CPF в логах, проверка
загружаемых файлов по MIME и расширению одновременно, приватное хранилище
документов.

Одноразовые коды: короткий срок жизни, лимит попыток, одноразовость, гашение
предыдущего кода новым, HMAC с серверным секретом вместо голого хеша (шесть
цифр — миллион вариантов, радужная таблица строится мгновенно), сравнение за
постоянное время.

Ключ для лимита запросов кода строится по нормализованному номеру, а не по
введённой строке: иначе «(11) 98765-4321» и «+5511987654321» получили бы
по своей корзине, и лимит обходился бы запятой. Запасной ключ по адресу
сводит IPv6 к подсети — у одного абонента там обычно целая /64, и сырой
адрес как ключ не ограничивает никого.

Ключи провайдеров существуют только на сервере. `OPENAI_API_KEY` никогда не
попадает в браузер, в бандл и в репозиторий.

## Mock-провайдеры

Без ключей работают заглушки (`MockAIProvider`, `MockOtpProvider`,
`MockStorageProvider`, `MockNotificationProvider`). Они **не притворяются**
рабочей интеграцией: `MockAIProvider` возвращает нулевую уверенность и пустые
структуры, `MockNotificationProvider` возвращает `delivered: false`, а
`MockStorageProvider` и `MockOtpProvider` отказываются запускаться в
production.

## Чего не хватает

| Что | Почему нельзя просто дописать |
| --- | --- |
| `DATABASE_URL` | база не создана: план Supabase упёрся в лимит проектов. Миграции при этом готовы и проверены на локальном PostgreSQL 16 — как только строка появится, `npm run db:deploy` поднимет схему |
| `OPENAI_API_KEY`, `OPENAI_MODEL` | ключ выдаёт владелец; в код не зашивается |
| Проверка на живом OpenAI | интеграция покрыта тестами на подменённом клиенте; что реальный API примет нашу форму запроса, без ключа проверить нельзя |
| Цифры прогона оценки | `npm run ai:eval` требует настоящего ключа. Сам прогон, проверки и вердикт покрыты тестами на подменённом клиенте; чисел о настоящей модели пока нет, и выдумывать их нельзя |
| Подтверждённые источники | `sources/candidates.json` содержит только главные страницы учреждений и ничего не подтверждает; ссылки на конкретные процедуры добавляет человек, который их открыл |
| Город в аналитике | `cityBucket` всегда пуст: город вместе с суммой, категорией и месяцем опознаёт человека не хуже имени, а для выбора канала он не нужен. Штат спрашивается, город — нет |
| Провайдер OTP | нужен договор с оператором |
| Логотип | `public/images/brand/` — плейсхолдер, см. README там |
| Растровые иконки PWA | нужны из утверждённого исходника |
| Реквизиты компании, DPO, текст договора | требуют юридической проверки; выдумывать нельзя |

## Деплой

Функции считаются в `gru1` (Сан-Паулу), рядом с базой в `sa-east-1`: иначе
каждый запрос к базе летит через океан.

Настройка production-деплоя относится к PHASE 13. Проект на Vercel пока
настроен на предыдущий стек и не связан с репозиторием, поэтому push сюда
ничего не разворачивает автоматически.
